## D2-A — SQL Server, contexts y aislamiento

1. **Alcance y exclusiones.** Una DB KDI de pruebas explícitamente designada, esquemas `identity`, `organizations`, `portfolio`, un DbContext propietario por módulo y tablas de historial de migraciones separadas. EF Core continúa como mecanismo; no Dapper, broker, DB distribuida, despliegue, datos reales ni migración automática al inicio. Entregar cadena de migraciones reproducible y procedimiento revisable; las tablas de negocio completas pertenecen a B/C. La versión/edición SQL y compatibilidad deben aprobarse antes de elegir paquetes o generar SQL.
2. **Decisiones para aprobar.** Recomendar una DB/esquemas/contexts separados frente a DB por módulo (consistencia distribuida innecesaria ahora) o contexto único (propiedad débil). Dueño de cada migración: módulo correspondiente; en D2-A los esquemas/contextos sin dependencias cruzadas no imponen orden entre módulos. Para B/C documentar un grafo de aplicación identity → organizations → portfolio solo cuando los artefactos y dependencias aprobados lo requieran; la flecha aquí significa precedencia de aplicación, no referencia de código. La historia de cada contexto reside en su esquema y solo su migrador la modifica. Describir por separado creación de esquemas/DB y migraciones de tablas. Aprobar operador y orden definitivo antes de primera aplicación. Recomendar no FK entre módulos inicialmente: referencias opacas y coordinador transaccional obligatorio; alternativa FK compuesta OrgId/ClientId exige propiedad y orden aprobados y no sustituye locks.
3. **Dependencias y riesgos.** Acceso a SQL real aislado; soporte/versiones compatibles de SDK, EF Core y proveedor pendientes de verificación. Deriva de esquema, permisos excesivos, collation que altere unicidad y pruebas contra otra versión son riesgos. Definir normalización de código por aplicación y collation de columna explícita, sin asumir collation del servidor. No compartir DB de desarrollo personal ni ambientes externos.
4. **Aceptación verificable.** A-01 instalación desde DB vacía y segunda ejecución sin cambios; A-02 cada contexto migra únicamente su esquema/historial; A-03 proceso de aplicación falla cerrado ante nombre/servidor distinto al autorizado; A-04 usuario de runtime carece de DDL; A-05 build/tests sin secretos en logs; A-06 script de actualización y recuperación revisado en DB desechable. No exigir downgrade destructivo como garantía: respaldo/restauración o recreación solo con permiso específico.
5. **Pruebas.** Unitarias para validación de configuración y guardas de destino; integración SQL Server para migraciones desde vacío y desde versión anterior, aislamiento de esquemas y restricciones; API para readiness sin exponer conexión/credenciales y fallo controlado; E2E smoke del host conectado al entorno aislado, sin UI de negocio todavía. SQLite/InMemory no sustituyen integración SQL Server.
6. **Presupuesto propuesto.** 10–16 horas-agente de implementación, 4–7 QA y 2–4 revisión independiente; total 16–27 horas-agente. Estimación, no autorización ni promesa temporal; incluye evidencia y correcciones pequeñas, excluye provisión y esperas. Tope inicial sugerido: 27 horas-agente con parada y decisión antes de excederlo.
7. **Infraestructura y permisos.** Human Orchestrator designa versión/edición/compatibility level, host, DB desechable, responsable, retención y canal seguro de secretos. Operador provisionador con permiso limitado de crear DB/esquemas; migrador con DDL limitado al destino; runtime con DML mínimo propuesto por esquema y sin DDL; con un solo principal compartido, los esquemas no constituyen una frontera fuerte de seguridad SQL entre módulos: la propiedad modular se asegura por política de aplicación y pruebas arquitectónicas. Identidad de pruebas separada y autorización explícita de limpieza. Elegir instancia existente dedicada o servicio/contenedor de SQL Server autorizado; ninguna opción se presume instalada o licenciada.
8. **Bloqueos.** Sin destino y propietario aprobados, sin autorización para DDL/limpieza, sin SQL compatible o restore oficial disponible: BLOCKED. No continuar B/C contra dobles para declarar aceptación SQL. D2-A puede autorizarse antes de IdP, con su exclusión explícita.

## D2-B — Identidad, membresías y permisos

1. **Alcance y exclusiones.** Integración OIDC, identidad local por par exacto `(issuer, subject)` con unicidad; nunca email como clave. Organizations posee membresía empresarial; Identity posee concesiones con OrgId/ProjectId opacos; coordinación Application valida ambas sin ciclo entre módulos. Selector de organización solo enumera membresías activas. No contraseñas propias, bypass productivo, SSO/usuarios de IDI, aprovisionamiento masivo, invitaciones por email ni privilegios globales implícitos.
2. **Decisiones para aprobar.** Recomendar BFF en el host ASP.NET Core existente, cookie de sesión Secure/HttpOnly, política SameSite compatible con callback, Authorization Code + PKCE también en cliente confidencial, tokens del IdP solo servidor, CSRF en mutaciones y sesión almacenada servidor. Comparar SPA Code + PKCE si existen consumidores/API separados: obliga política de tokens en memoria, renovación y CORS, y aumenta superficie browser. Aprobar mismo origen/reverse proxy o topología exacta antes de fijar cookie/CORS. Proveedor: Entra ID si ya existe tenant/administración empresarial aprobada; Keycloak si se aprueba operación propia; IdP OIDC gestionado si se aprueban costo/región/contrato. No seleccionar producto, plan ni versión sin esos datos. Proponer múltiples organizaciones por usuario; ninguna membresía implica escritura. Ratificar matriz de permisos y bootstrap administrativo fuera de endpoints públicos.
3. **Dependencias y riesgos.** D2-A aceptado, IdP/tenant de pruebas, TLS y callbacks autorizados. Validar issuer/audience/signature/tiempos, state/nonce y PKCE; issuer permitido no se toma de input libre. Riesgos: confusión de cuenta por email, sesión revocada conservada, autorización cacheada y acceso cruzado. Proponer comprobación de membresía y concesiones actuales por petición protegida y sesión local revocable. Expiración, idle timeout, máximo absoluto, logout local/remoto y objetivo de revocación del IdP requieren valores aprobados: no prometer revocación inmediata del IdP sin capacidad demostrada.
4. **Aceptación verificable.** B-01 identidad con mismo sub en distinto issuer no colisiona; B-02 sin login 401 en API, insuficiencia de permiso 403 y recurso ajeno 404 uniforme; B-03 OrgId manipulado no cambia alcance; B-04 revocar membresía/concesión impide siguiente petición protegida; B-05 cookie/token/CSRF y expiración cumplen política aprobada; B-06 logout invalida sesión local y no revela secretos; B-07 matriz rol × acción × alcance completa con denegación por defecto. El comportamiento IdP se acepta únicamente con cuentas de prueba reales autorizadas.
5. **Pruebas.** Unitarias de matriz, resolución iss/sub, pertenencia y scopes; integración SQL de unicidad y revocación; API autenticada con host aislado de pruebas para 401/403/404, CSRF, contexto y filtrado; E2E real OIDC login/logout, expiración y dos usuarios/organizaciones. Dobles prueban lógica, no acreditan interoperabilidad del proveedor. Ningún modo de prueba se incorpora como bypass al producto.
6. **Presupuesto propuesto.** 18–30 horas-agente implementación, 8–14 QA, 4–7 revisión; total 30–51. Tope sugerido 51; excluye configuración del tenant por terceros y esperas. Cambiar a SPA o añadir administración completa requiere reestimación.
7. **Infraestructura y permisos.** Operador IdP, cliente OIDC exclusivo de pruebas, redirect/logout URIs exactos, scopes mínimos, usuarios en al menos dos organizaciones y roles contrastantes; HTTPS y secreto/certificado si BFF confidencial. Canal de secretos fuera del repositorio; permisos separados de gestión IdP y ejecución. Aprobar cómo se crea primera organización/admin y quién revoca sesiones.
8. **Bloqueos.** Sin decisión de flujo/proveedor, tenant y cuentas aisladas, callbacks/TLS o matriz aprobada: no implementar autenticación ni aceptar B. Sin SLA de revocación medible, ese criterio permanece pendiente, no PASS.

## D2-C — Clientes, proyectos, auditoría y concurrencia

1. **Alcance y exclusiones.** KDI-R01–R08 y UC01–UC05: altas, lectura/listados, edición y archivo de clientes/proyectos, código único por organización, cliente obligatorio misma organización y Active/Archived, auditoría atómica y versión. Sin borrado físico, reactivación, transferencias de organización/cliente de proyecto, portafolios avanzados, reporting, outbox ni datos de IDI. Ratificar reglas aún propuestas antes de código.
2. **Decisiones para aprobar.** Recomendar índices únicos `(OrgId, NormalizedCode)` por entidad; códigos 32 y nombres 200 tras trim, normalización invariante y orden estable por código normalizado/ID. `rowversion` se emite como ETag fuerte opaco; GET detalle y respuesta de mutación incluyen ETag; PUT/archivo requieren un único If-Match vigente, sin wildcard. Ausente → 428; malformado → 400; obsoleto → 412; negocio/duplicado → 409. No exponer rowversion como fecha ni permitir que el cliente elija OrgId/estado arbitrariamente. Aprobar auditoría por módulo con actor local + iss/sub referencial, instante UTC servidor, acción/recurso/org, correlación y cambios permitidos redactados; retención y acceso se deciden con humano.
3. **Dependencias y riesgos.** A/B aceptados; aprobación explícita de concurrencia transversal: todos los comandos que alteren elegibilidad del cliente o proyectos activos usan una transacción SQL local y lock exclusivo sobre la fila de cliente mediante contrato Infrastructure específico, mantenido hasta commit (`UPDLOCK,HOLDLOCK` o mecanismo equivalente demostrado). Obtener locks por OrgId/ClientId estable; para varias filas ordenar IDs; luego proyectos en orden estable. Leer cliente bajo lock, validar estado/org, comprobar/modificar proyecto y persistir auditoría antes de commit. Archivo comprueba proyectos activos bajo el mismo protocolo. Crear/archivar/reactivar si se autorizara, y operaciones futuras que cambien cliente, deben participar; ningún atajo público omite coordinación. Contexts comparten conexión/transacción solo mediante adaptador coordinador, sin DbContext ajeno ni navegación EF entre módulos. Fallo de auditoría revierte negocio. Deadlocks/transitorios requieren política acotada que reinicie transacción completa sin duplicar mutaciones; nunca replay parcial. FK opcional refuerza existencia pero no estado. Índice Portfolio `(OrgId,ClientId,Status)` evita escaneos; prueba SQL concurrente decide suficiencia real, no revisión estática.
4. **Aceptación verificable.** C-01 AC01–AC13 del requisito con matriz aprobada; C-02 dos altas simultáneas de mismo código producen una sola fila; C-03 dos ediciones con mismo ETag producen una sola actualización; C-04 carrera alta de proyecto/archivo de cliente tiene exactamente un orden serial válido: nunca cliente archivado con proyecto activo; C-05 auditoría y mutación ambas commit o ambas rollback; C-06 recursos/listados/conteos de otra organización no son observables; C-07 errores API conservan Problem Details sin SQL/stack; C-08 UI conserva entrada ante 412 y exige recargar/reconciliar explícitamente.
5. **Pruebas.** Unitarias de estados, normalización, límites y coordinación por contratos; integración SQL de índices/collation/rowversion/rollback y carreras con dos conexiones y barreras deterministas (varios órdenes, sin sleeps como prueba); API de DTO inválido, 428/400/412/409/401/403/404, filtros, paginación estable y audit.read; E2E dos sesiones/organizaciones para CRUD permitido, denegación horizontal, archivo bloqueado y conflicto de edición. Incluir pruebas arquitectónicas de que módulos solo consumen fachadas, de coordinador sin camino alternativo y fixture negativo adicional de D1 como seguimiento separado autorizado, sin modificar candidato D1.
6. **Presupuesto propuesto.** 24–40 horas-agente implementación, 12–20 QA, 6–10 revisión; total 42–70, tope sugerido 70. Excluye rediseño de reglas y cambios de alcance. Priorizar evidencia de carrera y rollback antes de UI completa para descubrir bloqueo temprano.
7. **Infraestructura y permisos.** SQL y cuentas aislados de A, IdP/cuentas de B, dos sesiones browser, permiso de sembrar datos sintéticos y reset de DB dedicada, almacenamiento de evidencia redactada. Roles para lectura de auditoría y privilegios DML mínimos; runtime sin permiso de alterar esquema. Definir volumen representativo/latencia objetivo antes de afirmar rendimiento.
8. **Bloqueos.** Reglas de clientes compartidos/proyecto sin cliente/membresías no ratificadas, matriz ausente, SQL o IdP no operables, ausencia de prueba concurrente real o auditoría no atómica: aceptación C bloqueada. Ningún test omitido se convierte en PASS.

## Contratos HTTP propuestos para decisión

Base `/api/v1/organizations/{orgId}` validada contra identidad, membresía y permiso; orgId de ruta no concede acceso. `/clients`, `/clients/{clientId}`, `/clients/{clientId}/archive`; equivalentes `/projects`, `/projects/{projectId}`, `/projects/{projectId}/archive`. GET lista/detalle, POST alta, PUT edición y POST archivo, con If-Match en mutaciones existentes. No incluir reactivación. Identidad/contexto bajo `/api/v1/session` y `/api/v1/organizations` (solo organizaciones autorizadas); nombres/login/logout exactos dependen de BFF aprobado. Administración de membresías y concesiones requiere alcance separado aprobado; hasta entonces, provisionador de pruebas explícito, no endpoint administrativo abierto.

CreateClient: `code,name`; UpdateClient: `name` (cambio de código requiere decisión); CreateProject: `clientId,code,name`; UpdateProject: `name`. Respuestas: `id,code,name,status`, `clientId` para proyecto, ETag en cabecera; lista con `items,total,page,pageSize`, filtro code/name/status y tamaño máximo por aprobar. Si se necesitan versiones para acciones de lista, cada ítem incluye `etag` opaco con igual semántica. No aceptar actor/OrgId/version de auditoría en DTO. Auditoría expuesta solo por permiso y organización; no endpoint de búsqueda global implícito.

## Presupuesto y registro de ejecución

Las estimaciones anteriores son esfuerzo acumulado en horas-agente: A 960–1620 minutos-agente, B 1800–3060 y C 2520–4200. Incluyen una ronda acotada de correcciones tras QA/review; fallas estructurales o cambio de decisión requieren reestimación. No equivalen a duración de pared ni al costo monetario/tokens: concurrencia máxima dos especialistas, secuencia implementación → candidato congelado → QA/review, tiempos humanos/provisión y límites del proveedor impiden prometer calendario. Registrar consumo por agente y parar al tope aprobado, documentando avance y pendientes antes de pedir ampliación. El presupuesto de esta preparación documental es separado y no autoriza esos importes.

Para evidencia futura: `NOT RUN` significa prueba aún no intentada; `BLOCKED` significa no ejecutable por dependencia identificada (por ejemplo SQL/IdP ausente), con responsable y condición de desbloqueo; `FAIL` requiere ejecución con resultado negativo; `PASS` requiere ejecución verificable satisfactoria del candidato. Una suite con casos obligatorios BLOCKED/NOT RUN no acredita aceptación integral. D2-A no requiere IdP ni tablas de negocio completas; D2-B depende de A para sesiones/membresías persistidas; D2-C exige A+B sin bypass de autenticación para su cierre.
